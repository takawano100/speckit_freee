RULES

雇用形態で、何が変わるか

いちばん大きな分かれ目は勤怠管理をするかどうか。役員は打刻しない。労働時間が無いから割増も無く、36協定の対象にもならない。ここが決まらないと勤務体系が決められない。

○対象 ✕対象外 △要件を満たせば対象
項目 役員— 正社員— 契約社員— パート—
いま、パートの社会保険判定が間違っている疑いがあります。

比嘉 美穂（時給1,300円）を登録した直後、freeeは健康保険・厚生年金とも entried: false（対象外）と判定し、標準報酬をそれぞれ 58,000円・88,000円 に置きました。どちらもその保険の最低等級です。つまり pay_amount: 1300 を月額として扱った結果に見えます。

本来の判定は「週の所定労働時間が20時間以上か」「月額賃金88,000円以上か」で決まります。freeeは所定労働時間を知りません。勤務体系をまだ割り当てていないからです。週20時間なら月額は 1,300 × 86時間 = 111,800円 で、社会保険の対象になるはずです。

勤務体系を入れないと、社保の判定は正しくならない。勤務体系を割り当てたあとに entried が変わるかどうかを見れば、freeeが所定労働時間から判定し直すのかが分かります。変わらなければ、freeeは時給×所定時間を自分では計算していないことになります。

    結論 ✕ 使えない

    freee工数管理は、この事業所では動かない

    案件・工数・単価・人件費予算という名前はAPIの口として存在します。ただし工数管理が有効な事業所は0件でした。作らずに済ませる道はありません。

    GET /pm/users/me → {"id":1548****,"companies":[]} GET /pm/projects → 401 存在しないかすでに削除された事業所です

    だから 案件・工数・単価は、こちらで持つ。出発点は変わりません。

    結論 △ 器だけある

    勤怠タグは、口は開いているが中身が空

    読めます。ただし従業員に紐づくタグも、当日のタグも0件。返りのキーが複数形なので1日に複数付けられる形ではありますが、タグの定義そのものがまだありません。

    GET /employees/4174944/attendance_tags → {"employee_attendance_tags":[]} GET …/attendance_tags/2026-08-14 → {"employee_attendance_tags":[]}

    だから 「何の仕事か」の置き場になるかは、freeeの画面でタグを作ってからでないと決まりません。

    結論 ⚠ 見落としていた

    打刻がゼロでも、8時間が立っている

    打刻時刻は null なのに、勤務は9:00–18:00・480分として返ります。所定どおりとみなす設定が効いているためです。この480分は「働いた事実」ではありません。

    clock_in_at: null ・ clock_out_at: null normal_work_mins: 480 ・ use_default_work_pattern: true work_record_segments: [] ・ break_records: []

    だから 前日ぶんを翌朝に金額で見せるなら、打刻に基づく数字かみなしの数字かを、見分けて出す必要があります。

    GAP

    勤怠だけでは、どうやっても出ないもの

    上の棚に無いものだけを書きます。ここが要求の置き場です。

    • ✕ その時間が「何の仕事」だったか 勤怠には案件を入れる欄がありません。勤務の区切りという明細の器はあるのに、そこに指図書番号にあたるものが無い。
    • ✕ 1時間あたりいくらか 金額が出るのは給与の段だけで、しかも月に一度。前日ぶんを翌朝に出すなら、月次の確定給与は間に合いません。
    • ✕ 会計のどこに載せるか 部門も勘定科目も会計側にあります。勤怠から仕訳までは、APIの上でつながっていません。
    • ✕ その数字が「働いた事実」かどうか 打刻がなくても所定どおりの分数が立ちます。打刻漏れも、あとからの修正も、承認の遅れも起きる。何をもって「その日の数字」とするかは、freeeの外の決めごとです。

    どれも「動かない」ではなく「動いたように見えて違う」種類の詰まり方だった。エラーが出ないぶん質が悪い。

    POSTの返り値が壊れている

    同じ形のPOSTでも level が 2 のときと −1 のときがある。さらに、親を渡していないのに身に覚えのない親IDが返ってきた。保存そのものはすべて正しい。返り値だけが違う。

    POST /api/v1/groups {"group":{"name":"プロダクト本部","code":"D200"}} ← 親を渡していない → {"id":918836, "level":-1, "parent_group_id":911051} ↑ 作った覚えのないID GET /api/v1/groups → {"id":918836, "level":1, "parent_group_id":null} ↑ 実際はこちらが正しい

    教訓POSTの返りを次の処理へ渡してはいけない。作ったらGETで読み直す。もしこの parent_group_id を次のPOSTに使っていたら、存在しない親にぶら下がる部署ができていた。

    所属を渡しても、黙って捨てられる

    従業員を作るとき group_id と position_id を添えた。エラーも警告も出ず 200 が返った。そして所属は空のままだった。更新でも同じだった。

    POST /api/v1/employees {"employee":{ …, "group_id":918839, "position_id":219965 }} → 200 {"employee":{"id":4211185, …}} ← 何も言われない GET /api/v1/employees/4211185/group_memberships → {"group_memberships":[],"total_count":0} ← 空

    教訓知らない項目を無視して 200 を返す。送った値が効いたかどうかは、必ず読み直して確かめるしかない。

    PUTは部分更新ではなく、履歴の追加

    肩書きだけ直そうとしたら、氏名が無いと弾かれた。送らなかった項目は消える前提の全置換。しかも id が変わる。上書きではなく、履歴を1本足している。だから year と month が要る。

    PUT /api/v1/employees/4211185/profile_rule {"employee_profile_rule":{"title":"部長"}} → 400 last_name, first_name, last_name_kana, first_name_kana が指定されていません。 氏名を添えて再送 → 200 profile_rule.id 9497882 → 9497893 ↑ 別レコードになっている

    教訓PUTの前にGETして、返ってきた全項目に差分を乗せて送り返す。これをやらないと入力済みの情報が静かに消える。

    画面の自動操作は、タブが見えていないと止まる

    所属をブラウザ操作で入れるループが1件目で止まった。Chrome はバックグラウンドのタブで setTimeout を1分に1回まで絞る。待ち時間がすべて60倍に伸びていた。

    await new Promise(r => setTimeout(r, 3000)) ↑ 裏タブでは 3秒 が 60秒 になる const wait = ms => new Promise(res => { const end = Date.now() + ms, ch = new MessageChannel(); ch.port1.onmessage = () => Date.now() >= end ? res() : ch.port2.postMessage(0); ch.port2.postMessage(0); }); ← これなら絞られない

    教訓画面の自動操作は、APIと違って「環境」に依存する。同じコードが表と裏で60倍違う速さになる。設定画面はハッシュだけ変わって描画されず、所属の行の操作セルは spinner のまま返ってこない。3つの症状が同じ1つの原因だった。これはAPIには無い種類の壊れ方。翌日、これは「遅くなる」ではなく「静かに落ちる」だと確定した。
